# B01 — первый вертикальный срез

Статус: not_started. Выполняется после короткой диагностики.

## Контекст

Делаем сервис бронирования. Для начала администратор должен создать ресурс для бронирования (например, переговорную) и получить его по ID. Авторизацию вводим отдельным этапом: этот срез работает только в учебной локальной среде.

## Твоя задача

В `practice/booking-service/` создай минимальный проект на FastAPI и PostgreSQL. Выбери совместимые версии Python/библиотек, зафиксируй зависимости и объясни выбор sync/async. Используй Pydantic 2, SQLAlchemy 2, Alembic, pytest/HTTPX и Docker Compose.

Контракт:

- `POST /resources`: принимает `name` (после удаления крайних пробелов от 1 до 100 символов); сохраняет запись; возвращает 201 и `id`, `name`.
- `GET /resources/{id}`: для существующего ID возвращает 200 и запись; для отсутствующего корректного ID — 404; для некорректного формата — 422. Формат ID выбери и опиши.
- `GET /health/live`: подтверждает, что приложение обслуживает запросы, без проверки БД.
- `GET /health/ready`: проверяет доступность БД; возвращает 200 или 503, не раскрывая реквизиты подключения.

Уникальность имени пока не требуется. Таблицу создаёт миграция, а не неявный `create_all` при старте приложения.

## Критерии приёмки

1. README содержит команды установки, запуска, миграции и тестов. Проверен запуск из пустой учебной БД. Команда или документированный сценарий запуска воспроизводим.
2. API выполняет контракт; сохранённый ресурс доступен после перезапуска приложения.
3. Интеграционные тесты используют отдельную PostgreSQL БД: создание/чтение, неизвестный ID, неверный ID, пустое имя, имя длиннее 100 символов. Тесты повторяемы и не трогают рабочие данные.
4. Проверено, что недоступность БД отражается в readiness, а liveness продолжает работать. Зависшие подключения ограничены таймаутом.
5. Настройки читаются из окружения, секреты не попадают в Git, примеры конфигурации содержат только безопасные локальные значения.
6. Логи позволяют связать ошибку с запросом и не раскрывают секреты. В ответах нет stack trace.

Объясни: где закрывается сессия БД; кто владеет транзакцией; почему выбранные тесты могли бы поймать дефект; чем readiness отличается от liveness. После ревью наставник выдаст небольшое изменение контракта для самостоятельной реализации. Оно не должно быть заранее решено агентом.
